# AI Usage

## Tools used

- **Claude (claude.ai, with code execution)**: generated the initial version of the project, ran the test suite and checked the UI in a headless browser.
- **Claude Code (CLI, Claude Opus 5.5)**: used for the review, tests and fixes described under "Changes made by me" and "Found during review with Claude Code" below.

## How I used the coding agent

The initial version was generated in one session from the assignment PDF. The agent planned the structure, wrote the backend, frontend, tests and documentation, then ran the tests and drove the UI in a headless browser to find problems.

I then worked with Claude Code in a single session, in four steps:

1. **Review without edits.** I asked it to read the whole repository and explain the request flow for `POST /api/assistant/query` file by file, pointing out anything wrong or fragile, without editing files. It traced the request from `frontend/app.js` through the route, the assistant service, the LLM agent and client, the rule-based assistant, the tools, validation and the repository. It confirmed two bugs by running a throwaway script against a temporary database, and listed fallback gaps and other fragile spots.
2. **Git checkpoint.** Before any change, I had it initialise a git repository and commit the untouched generated code (`7db7212`).
3. **Tests first, then fixes.** I chose which findings to fix and asked for failing tests first, with proof that they failed, then the fixes, then a full test-suite run and a commit (`46d6827`).
4. **Documentation.** I asked it to bring `README.md` and this file up to date with what happened.

## Changes made by me

These are my decisions; Claude Code wrote the code and text.

- **Set up a git checkpoint first.** Before changing anything, I had the untouched generated code committed as "Initial version generated with Claude (chat)", so every later change is a reviewable diff against it.
- **Asked for tests before fixes.** For every fix, I required a failing test first and the test output showing the failure, then the fix, then a full test-suite run.
- **Chose which issues to fix.** From the review I chose the two confirmed rule-based bugs, the gaps in the LLM fallback, and the handling of `stop_reason == "max_tokens"`. The other findings are left as known limitations, listed below.
- **Kept the Co-Authored-By lines.** Commits made by Claude Code end with a `Co-Authored-By: Claude Opus 5.5` line, and I chose to keep them.
- **Verified the fix in the running app.** After the fixes, I started the server and asked the assistant 'How much did I spend in the last 0 days?' in the browser. It returned the 'couldn't work out a valid time period' answer instead of a server error.

## Problems encountered

### Found and fixed during the initial generation

These are real problems in the agent's first drafts, caught by running the code, the tests, and a headless browser:

1. **Files written to the wrong directory.** The agent created folders with `mkdir -p dir/{a,b}`, but the shell was `sh`, which does not support brace expansion. The command created no folders and the following file writes landed in `/`. Fixed by creating directories explicitly and moving the files.
2. **Questionable SQL.** The first draft of the search filter used `LIKE ? ESCAPE '\' COLLATE NOCASE`. The `COLLATE` clause was unnecessary (SQLite `LIKE` is already case-insensitive for ASCII) and its placement after `ESCAPE` was not something to rely on. Removed; a test now checks case-insensitive search and that a literal `%` is not treated as a wildcard.
3. **Convoluted parsing logic.** The first `extract_top_n` in the rule-based assistant re-assigned the same variable through chained conditionals and was hard to verify. Rewritten as two clear regex checks, with unit tests for "three largest", "top 5" and "the 2 most expensive".
4. **Wrong answer type.** "Show me travel expenses in September" returned a total instead of a list, because there was no "list" intent. Added one, backed by `search_expenses`, with a test.
5. **Misleading chart.** In the category chart each bar's track had a different length, because each row sized its amount column independently, so bars were not comparable. Fixed with a fixed-width value column. Found from a screenshot.
6. **Mobile horizontal overflow.** On a 390px-wide screen the page scrolled sideways. Measuring element positions in the browser showed that a visually-hidden table header label was positioned relative to the page instead of the table's scroll container. Fixed by adding `position: relative` to the container (plus `min-width: 0` on grid children).

One pitfall was handled before it became a bug: on Python 3.11+, `date.fromisoformat("20261015")` succeeds, so a naive validator would accept dates outside the `YYYY-MM-DD` format. The validator checks the exact shape first, and a test covers it.

To check that the tests detect real bugs, the month-boundary calculation was deliberately broken (off by one day). 8 tests failed, then passed again after reverting.

### Not verified in the initial session

- **The live Claude API path was not exercised.** The sandbox had no network access, so the tool-calling loop was tested only against a scripted fake API (which checks request shape, tool results, error recovery, fallback and the step limit). It was still not run with a real key in the Claude Code session: no `ANTHROPIC_API_KEY` was used, and the new fallback tests also rely on the fake API or a mocked `urlopen`.

### Found during review with Claude Code

Claude Code found these in the review I asked for. Each bug was confirmed by running code: the first two with a throwaway script before any edits, all of them with a failing test.

1. **The rule-based assistant returned 500 for impossible time periods.** "How much did I spend in the last 0 days?" produced a start date after the end date, so tool validation raised a `ToolError` that nothing caught. "What did I spend in january 0000?" raised a `ValueError` from `date(0, 1, 1)`. The rule-based assistant is also the fallback, so this crashed even when Claude was configured. Fixed: `extract_period` raises a `PeriodError` that the assistant turns into a "couldn't work out a valid time period" answer, and tool validation errors are caught and listed as failed calls.
2. **Wrong wording without a category.** With no category or payment method, the answer read "You have no all expenses recorded yesterday." Fixed.
3. **The LLM fallback only caught `LLMError`.** A connection reset or `RemoteDisconnected` while reading the response, an undecodable response body, response content that was not a list of objects, a `tool_use` block without an `id`, and a database error inside a tool all returned 500 instead of falling back to the rules. Fixed: the transport maps these network and decoding errors to `LLMError`, the response shape and tool ids are checked, and any other unexpected error is logged and falls back with a generic `fallback_reason`, so internal details are not sent to the client.
4. **Truncated answers were shown as complete.** A response with `stop_reason == "max_tokens"` was returned as a normal answer. It now raises `LLMError`, so the rules assistant answers instead.

The 8 tests for these were written first and run before any code change. All 8 failed with the predicted causes (500s from the uncaught `ToolError`, `ValueError`, `ConnectionResetError`, `UnicodeDecodeError`, `AttributeError` and `OperationalError`; the "no all expenses" wording; and the truncated answer tagged `anthropic`). After the fixes, all 72 tests passed.

Mistakes Claude Code made and caught itself in this session:

- **A meaningless assertion in its own test.** The first version of the truncation test asserted `assertNotIn("You spent ₹3,", ...)` against a sliced and padded copy of the answer. That could not detect anything useful, because the correct fallback answer also starts with "You spent ₹3,500.00". It noticed this before running the tests and replaced it with an exact `assertNotEqual` against the truncated text.
- **A sibling bug its review missed.** The review reported only the "no all expenses" wording. While reviewing its own diff, it found the same problem in the count answer: "You recorded 4 all expenses this month". It wrote a 9th test, showed that it failed, and fixed both sentences with a shared qualifier. Full suite: 73 passed.

Left as known limitations (found in the review, not fixed):

- No overall time limit per question: each API call has a 30-second timeout and the loop allows 6 calls, so one request can take about 3 minutes.
- For API errors, `fallback_reason` still includes up to 300 characters of the raw Anthropic error body, which the UI displays. Only unexpected errors use the generic message.
- `get_category_breakdown` filters only by date, so a question like "what share of my UPI spending went to marketing?" cannot be answered correctly. For list and top-N questions, the rules assistant uses only the first category it finds. A `limit` of `3.0` is rejected as not an integer.
- Tool results rebuild paise from float rupees (`round(amount * 100)`), and `json.dumps` escapes "₹" as `₹` in what the model receives.
- The route checks the 500-character limit before stripping whitespace.
- Expense descriptions are sent back to the model in tool results, so a description could contain instructions (prompt injection). The tools are read-only and the app has a single user, so the impact is limited to a misleading answer.
- The live Claude API path has not been run (see above).
